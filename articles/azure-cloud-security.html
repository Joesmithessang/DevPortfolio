Securing the Cloud: What a Microsoft Azure Health-Check Revealed

The common cloud setup mistakes that quietly leave organizations exposed — and the practical fixes — explained clearly for both cloud teams and the leaders who fund them.

Joe Smith-Essang Platform: Microsoft Azure Cloud Security Assessment 10 min read
In Plain Terms
“The cloud” just means running your systems on a provider's computers (here, Microsoft Azure) instead of your own. The catch: the cloud gives you hundreds of settings to configure, and the defaults often favour convenience over security. A misconfiguration is simply one of those settings left in an unsafe state — like a door left unlocked. Most cloud breaches aren't clever hacks; they're someone finding a door the owner forgot to lock.

Why Simple Cloud Mistakes Cause Big Breaches

When you run your own servers in your own building, a firewall at the edge does much of the protecting. The cloud works differently: you're responsible for correctly configuring hundreds of separate services, and each one ships with default settings that lean toward “easy to use” rather than “secure.” It's surprisingly easy to move to the cloud and accidentally leave more doors open than you ever had before.

This article shares the patterns from a thorough security check of an Azure environment, covering five areas: who can log in, network protection, the servers and apps themselves, stored data, and whether anyone is watching for trouble. The full checklist covered more than 90 individual settings. Nothing here is tied to any specific organization.

The Single Biggest Problem
The most serious finding of the whole review: 69% of user accounts had no second login step (MFA) turned on. In the cloud, a password is often the only thing standing between an attacker and your systems. Without a second step, one stolen or guessed password is enough to walk right in — and this affected most of the organization.

Area 1 — Who Can Log In

In the cloud, controlling who can log in is the most important protection you have. Almost every action starts with someone signing in, so if login security is weak, everything else is built on sand.

Login & Account Security
The foundation of cloud security
  • Most accounts (69%) had no second login step — including accounts that could reach live business systems
  • Tools to spot suspicious logins (like a sign-in from an unusual country) were available but never switched on
  • The system for tightly controlling powerful admin accounts was set up — a good sign — but needed the right licence to work fully
  • Login rules existed but had never been reviewed for gaps or conflicts
  • Databases relied only on their own local passwords instead of the central, better-protected login system

Area 2 — Network Protection

Azure uses a kind of built-in firewall (called a Network Security Group) to control which connections are allowed to reach your systems. Think of each rule as a door: it should only be open to the people who genuinely need it. Leaving these doors open to the entire internet is one of the most common and dangerous cloud mistakes. The table below lists the open doors we found; it's detailed for technical readers, but the pattern is simple — too much was left open to everyone.

Guarding the front door of web apps
  • Old, weak encryption still allowed — can be downgraded and broken by attackers
  • No web application firewall switched on — nothing filtering out common attacks against the websites
  • Only basic protection against traffic-flooding attacks — the stronger tier is recommended for important systems

Area 3 — The Servers and Apps Themselves

Virtual Servers
The machines running in the cloud
  • No security software installed on the servers to detect malware or attacks
  • Server hard drives not encrypted — the data could be read if the underlying storage were ever accessed
  • Leftover drives from deleted servers left unencrypted, still holding old data
  • Servers not set up to survive a hardware failure — no backup if the equipment fails
Web Applications
The apps users interact with
  • No login required to reach some apps
  • Visitors not forced onto the secure (encrypted) version of the site
  • Apps storing fixed passwords in their settings instead of using safer, automatic credentials
  • Software components running on outdated versions (PHP, Python, Java, and others)
  • Old, weak encryption still permitted instead of requiring the modern standard
Container Platform (Kubernetes)
A system for running apps at scale
  • No limits on what logged-in users could do — anyone with access could take any action
  • Weak separation between the different apps running on the platform
  • Internal services needlessly exposed to the outside
  • No monitoring — no visibility into the platform's health or unusual activity
  • Node pool count below 3 — insufficient resilience for production workloads

Area 4 — Stored Data and Databases

Databases

  • No record kept of who accessed the database — nothing to review for compliance or investigations
  • No alerting for suspicious database activity
  • Stored data not encrypted — readable if the storage is ever accessed directly
  • Access records kept too briefly — well short of the 12 months most regulations require
  • The database was reachable by too many internal systems — access should be limited to only those that truly need it
  • No email alerts set up for security warnings

The Secrets Vault (where passwords and keys are stored)

  • Stored passwords and keys had no expiry date — so they never got refreshed automatically
  • No record of who accessed the vault or when
  • Accidental deletion would be permanent — recovery protection wasn't switched on

File Storage

  • Storage open by default — reachable from anywhere unless specifically blocked
  • Some stored files were publicly readable — accessible to anyone on the internet, no login needed
  • Even the access records themselves were public
  • Data could be transferred unencrypted rather than only over secure connections
  • No logging of who read, changed, or deleted files
Why the Public Files Were So Serious
Some stored files were readable by anyone on the internet — and so were the records of who had accessed them. That combination means an attacker could not only take the data, but also study the access patterns to plan their next move, all without ever logging in.

Area 5 — Watching for Trouble

You can't respond to an attack you never notice. Detecting, investigating, and responding all depend on keeping good records and having alerts switched on. Across the board, this environment had Microsoft's built-in cloud security monitoring barely configured.

Security Monitoring — What Was Missing
Whether anyone would notice an attack
  • The monitoring tool was left on its free, limited mode instead of the fuller paid version
  • Servers weren't automatically enrolled into monitoring, so many went unwatched
  • The tool wasn't checking whether protections like encryption and anti-malware were actually in place
  • Known weaknesses on servers weren't being gathered up and flagged
  • Records were kept for less than a year — short of what most regulations require
  • No emergency contact was set, so critical alerts had nowhere to go
  • No alerts for important changes, like someone altering the firewall rules
The Bottom Line on Monitoring
With traffic logging off, the monitoring tool barely configured, and no alerts set up, an attacker moving through this environment would have triggered no automatic alarms at all. The only way to catch them would be to manually dig through logs — assuming any were even being kept.

A Fix-It Plan, in Priority Order

 First (within a week)

Turn on a second login step for everyone. Close off remote admin access from the internet. Encrypt the databases. Make storage private. Set an emergency security contact so alerts reach someone.

 Soon (within a month)

Upgrade to the fuller monitoring tier and switch on traffic logging. Keep records for at least a year. Turn on access logging for the secrets vault and set expiry dates. Force all websites onto secure connections.

 Ongoing (within three months)

Encrypt all server drives. Limit what users can do on the container platform. Update outdated software. Add smarter login rules that react to risky sign-ins. Turn on database threat alerts with email notifications.

Recommendations for Cloud Teams

Make a Second Login Step Mandatory

Require a second login step for every user, no exceptions — enforced by policy, not left to people to opt in. For the most powerful accounts, use physical security keys, which are the hardest to defeat.

Open Only the Doors You Need

Start with everything closed and open only what's genuinely required — never open access to the whole internet by default. Review these firewall rules every few months and close anything no longer needed.

Pay for Proper Monitoring

The free monitoring tier barely protects you. The paid tier adds real threat detection and alerting. Given what a breach costs, the extra spend is easily justified.

Keep Secrets in a Proper Vault

Store all passwords and access keys in a dedicated secure vault — never in app settings or code. Log who accesses them, set expiry dates, and refresh them automatically.

Encrypt Everything You Store

Encrypt server drives, databases, and stored files, and only allow data to move over secure connections. Treat unencrypted storage as simply unacceptable.

Plan Your Record-Keeping First

Decide what you'll log and for how long before you build anything. Send all your logs and alerts to one central place, and keep them for at least a year.

Key Takeaways

  • Cloud security is ongoing, not a one-time setup. Unsafe settings stay unsafe forever unless something is continuously checking for them. Use automatic checks to catch problems as they appear.
  • The defaults are not safe. Cloud services arrive set up for convenience, not security. Harden every service against a known security checklist before it goes live.
  • Login security matters most. With most accounts lacking a second login step, everything else was undermined. One stolen password could have meant a full takeover.
  • No monitoring means no security — just hope. Turning off logs and alerts doesn't reduce risk; it just removes your ability to notice and respond when something goes wrong.
  • Prevent bad settings, don't just report them. Most cloud platforms let you automatically block unsafe setups from being created in the first place. Use that, rather than only flagging problems after the fact.
